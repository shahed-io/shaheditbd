# Customer Data Encryption System

## Goal
Encrypt sensitive customer data at rest so that even someone with raw database access sees only ciphertext. Only the owning customer and admins can view plaintext, always through server-side gated functions.

## Approach
- **Cipher:** `pgcrypto` `pgp_sym_encrypt` (AES-256, authenticated) — battle-tested, built into Postgres.
- **Key:** One master key generated by Lovable and stored in Supabase Vault (`app.encryption_key`). Never exposed to client, never logged, not readable by anon/authenticated roles.
- **Access:** All decryption goes through `SECURITY DEFINER` functions that verify `auth.uid() = owner_id OR has_role('admin')`. Direct SELECT on the encrypted columns returns only ciphertext (bytea) — useless without the key.

## Scope of encryption

| Table | Fields encrypted |
|---|---|
| `license_keys` | `key_value`, `extra_info` |
| `order_items` | `license_key` (delivered credential shown to buyer) |
| `personal_licenses` | login/email/password fields |
| `orders` | `customer_phone`, `customer_email`, `shipping_address`, `notes` |
| `bkash_transactions` | `trx_id`, `payer_reference`, `payer_account` |
| `payment_proofs` | `transaction_id`, `sender_number` |
| `support_tickets` | `subject`, `message` |
| `support_replies` | `message` |

## Implementation steps

### 1. Key infrastructure
- Generate 64-char master key → store in Vault as `app_encryption_key`.
- Create helper functions:
  - `public._enc(text) → bytea` — encrypts with vault key.
  - `public._dec(bytea) → text` — decrypts; only callable by SECURITY DEFINER functions.
- Both marked `SECURITY DEFINER`, `search_path = public`, `REVOKE EXECUTE FROM public/anon/authenticated`.

### 2. Add ciphertext columns
For each table above, add `<field>_enc bytea` columns alongside the existing text columns.

### 3. Backfill migration
Loop through existing rows and populate `<field>_enc = _enc(<field>)`. Runs once inside a single migration.

### 4. Sync triggers
`BEFORE INSERT OR UPDATE` triggers on each table auto-encrypt: if plaintext column changes, mirror to `_enc`, then blank the plaintext column (store `'***'` placeholder for legacy queries that still SELECT the column).

### 5. Owner + admin decrypt RPCs
Create per-table `SECURITY DEFINER` functions:
- `get_my_license_keys(order_id)` — returns decrypted keys only if `orders.user_id = auth.uid()` or admin.
- `get_order_secure(order_id)` — returns decrypted contact + address for owner or admin.
- `admin_get_license_key(license_id)` — admin only.
- `get_my_support_thread(ticket_id)` — owner or admin.
- `get_my_personal_licenses()` — owner or admin.
- `admin_get_bkash_transaction(id)` / `admin_get_payment_proof(id)` — admin only.

Each RPC calls `_dec()` internally and returns plaintext in the JSON response.

### 6. Wire up the app
Replace direct table reads of these sensitive fields with the RPCs:
- User dashboard (orders, licenses, personal licenses, support) → `get_my_*`.
- Admin panel (orders, licenses, bKash, payment proofs, support) → `admin_get_*`.
- Order confirmation / email invoice / WhatsApp invoice edge functions → call service-role RPC.
- Checkout writes plaintext into the normal column — trigger encrypts and clears it automatically.

### 7. Lock down plaintext columns
After backfill + code is switched over, revoke SELECT on the plaintext columns from `anon` and `authenticated` (keep for `service_role` for maintenance). RLS + column privileges together mean even a leaked anon key sees nothing.

### 8. Rotation-ready
Master key is versioned (`_enc` writes a `v1:` prefix). A future rotation function can decrypt `v1` and re-encrypt as `v2` without downtime.

## What will NOT change
- Product data, prices, categories, blog content — public info, no encryption.
- Search, filters, order totals — those use non-sensitive columns.
- Auth passwords — already hashed by Supabase Auth (never stored plaintext).
- Bengali brand-name normalization and all UI/design.

## Risk & downtime
- Backfill migration touches every historical row in the listed tables. Expected time: under a minute for the current data size.
- Brief window (a few seconds) during migration where sensitive columns are read-locked. No user-visible downtime.
- If the master key is ever lost, encrypted data becomes unrecoverable — Lovable Cloud Vault stores it durably, and it will be listed in Cloud secrets so you can back it up.

## Technical details

- `pgp_sym_encrypt(plaintext, key, 'cipher-algo=aes256, compress-algo=1')`.
- Vault access via `SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name = 'app_encryption_key'` — restricted to SECURITY DEFINER helpers.
- `EXCEPTION WHEN OTHERS` around every decrypt so a corrupt row never breaks a page load — returns `'[unreadable]'` and logs a warning.
- Two-column pattern (`col` + `col_enc`) is temporary; once code is fully migrated we can drop the plaintext columns in a later cleanup migration.

## Order of execution
1. Migration A: key + helpers + all `_enc` columns + backfill + encryption triggers + decrypt RPCs + privilege revokes.
2. Code update: switch every read site to the new RPCs.
3. Verify with real user + admin sessions.
4. Later cleanup migration: drop plaintext columns once nothing references them.
